# 全库并发与增量导入

## Goal

在 Windows 版 Navidrome 浏览器中显著缩短“添加全部”的等待时间，并在完成一次可靠基线导入后，让后续操作通常只读取和追加服务器新增歌曲。

## Background and Confirmed Facts

- 上一任务已经实现完整艺术家库递归、进度、失败汇总、关闭取消和一次性播放列表写入。
- 用户已在真实环境验证“添加全部”能够正常加入歌曲，但现有“艺术家→专辑→歌曲”的顺序网络请求耗时较长。
- OpenSubsonic 没有歌曲级变更游标；`getIndexes(ifModifiedSince)` 只控制艺术家索引返回，`getAlbumList2(newest)` 不能保证捕获旧专辑中新歌。
- Navidrome 当前实现支持 `search3` 空查询分页，并按 `media_file.rowid` 自然顺序返回歌曲。该顺序属于 Navidrome 实现特性，不是 OpenSubsonic 协议保证。
- 用户选择方案 A：采用 Navidrome 快速尾部增量，并在状态或锚点异常时自动执行完整核对。
- 本任务继续仅处理 Windows 组件。

## Requirements

### R1. 快速全库枚举

- 优先使用 `search3` 空查询的大页分页枚举歌曲，避免逐艺术家、逐专辑请求全库。
- 分页枚举前后读取 Navidrome `getScanStatus`，扫描进行中或 `lastScan` token 变化时不得接受本轮结果。
- 相邻页使用重叠边界并验证预期重复项；任何非预期跨页重复、边界失配或无进展都视为分页期间集合不稳定。
- 若服务器不支持该分页能力，则保留现有递归路径作为兼容回退。
- 递归回退使用固定上限并发，避免无限并发压垮服务器。

### R2. 增量语义

- “新增歌曲”定义为：当前服务器返回的 song ID 不在该服务器和用户的持久化精确 ID 集合中。
- 同一 song ID 的标题、专辑或其他元数据变化不视为新增。
- 已删除歌曲不从 foobar2000 播放列表中移除。
- 被服务器重新创建并获得新 song ID 的歌曲视为新增。

### R3. 自动模式选择

- 现有“添加全部”按钮自动选择：首次完整导入、有效基线上的快速尾部增量，或检测异常后的完整核对。
- 快速增量从旧尾部附近开始分页，并用已保存的有序尾部锚点验证分页连续性。
- 服务器类型或版本、用户、可访问音乐库范围、状态格式、状态内容或锚点不匹配时，不得继续信任尾部游标，必须自动退回完整核对。
- 增加“完整核对”入口，强制分页扫描当前全库、只追加未记录 ID，并用成功结果重建基线。

### R4. 持久化与隔离

- 第一次成功完整导入后，在 foobar2000 profile 下持久化精确歌曲 ID 集合、当前游标数量、有序尾部锚点、服务器信息和可访问音乐库指纹。
- 状态按规范化服务器 URL + 用户名隔离；状态中不得保存密码、salt、认证 token 或自定义请求头内容。
- 大型 ID 集合使用组件专用状态文件，不塞入 `cfg_string`。
- 状态先写临时文件，再原子替换正式文件；损坏或不兼容状态必须可安全忽略并进入完整核对。
- 状态提交前校验加载时的文件 generation，防止状态在任务期间被其他写入覆盖。

### R5. 原子完成与生命周期

- 导入任务开始时快照服务器配置，单次任务不得混用运行中途修改的新旧配置。
- 独立窗口和嵌入偏好页对同一服务器 + 用户只能有一个全库导入；第二个入口显示忙碌且不得读取或提交同一状态。
- 递归回退必须使用配置快照重新获取艺术家根，并把快照贯穿艺术家、专辑和歌曲请求，不复用可能属于旧配置的 UI 树根。
- 只有枚举完整成功、未取消且新状态临时文件准备成功时，才允许在主线程追加播放列表并提交新状态。
- 播放列表追加必须返回可回滚的 playlist/index/count receipt；正式状态替换失败或 generation 冲突时，立即同步移除本次追加范围，确保用户最终看不到半提交结果。
- 临时状态文件和同身份导入锁使用 RAII 所有权；窗口销毁、消息丢弃、异常或取消路径必须自动释放。
- 部分请求失败、分页不前进、状态准备失败或窗口关闭时，不得提交不完整基线。
- 保留忙碌保护、进度反馈、关闭取消和最终一次性播放列表写入。

### R6. 兼容性与范围

- 不改变现有 `navidrome://track/...` URI、已有服务器配置字段、单项添加、立即播放、搜索、刷新、右键菜单和 Enter 行为。
- 不改变 macOS/Linux 行为，不新增服务端依赖。
- 所有新增 Windows 用户界面文字继续集中在 `Windows/Localization.h`。

## Acceptance Criteria

- [ ] AC1：支持 `search3` 空查询分页的 Navidrome 服务器不再逐艺术家、逐专辑获取全库歌曲。
- [ ] AC2：第一次“添加全部”完整导入可访问歌曲并生成持久化基线。
- [ ] AC3：无新增歌曲时第二次点击“添加全部”不重复追加，并显示已是最新或新增 0 首。
- [ ] AC4：向新专辑或旧专辑加入歌曲后，再次点击只追加具有新 song ID 的歌曲。
- [ ] AC5：快速增量验证尾部锚点；验证失败、服务器版本变化、音乐库范围变化或状态损坏时自动完整核对。
- [ ] AC6：“完整核对”扫描全库、仅追加基线中不存在的 ID，并成功重建当前精确 ID 集合和尾部锚点。
- [ ] AC7：兼容递归回退使用固定并发上限；所有模式下 UI 保持响应，任务可取消。
- [ ] AC8：枚举失败、分页异常、状态写入准备失败或取消时，不修改播放列表且不提交新基线。
- [ ] AC9：正式状态替换失败或 generation 冲突时，本次播放列表追加被同步回滚，旧状态保持不变。
- [ ] AC10：状态按服务器 + 用户隔离，不包含密码、token 或自定义请求头；正式文件通过临时文件原子替换。
- [ ] AC11：独立窗口与嵌入偏好页同时触发同一身份导入时只有一个任务执行，另一任务显示忙碌，不重复追加且不丢失状态更新。
- [ ] AC12：分页期间扫描开始/完成、相邻页边界失配或非预期跨页重复时，本轮结果被丢弃并最多重试一次；仍不稳定则不追加、不提交。
- [ ] AC13：窗口在临时状态准备后销毁时，RAII 自动删除临时文件并释放身份锁，不访问失效 HWND。
- [ ] AC14：递归回退在运行中修改配置时仍全程使用启动快照和重新获取的根，不混用旧 UI 根与新配置。
- [ ] AC15：删除服务器歌曲不会删除播放列表项目；同 ID 元数据变化不会重复追加。
- [ ] AC16：状态 codec 截断/超限/重复 ID、分页漂移、提交失败和双窗口并发都有可重复的故障注入验证。
- [ ] AC17：原有单项添加、立即播放、搜索、刷新、右键菜单、Enter 和 `navidrome://` 播放不回归。
- [ ] AC18：Windows `Release|x64` DLL 和 `.fb2k-component` 重新构建并通过 PE、包结构和 SHA-256 完整性验证。

## Out of Scope

- 服务端插件、修改 Navidrome 数据库或调用 Navidrome 私有管理 API。
- macOS/Linux 增量导入。
- 自动删除、移动或整理播放列表中的旧歌曲。
- 在多个 Windows 设备之间同步导入状态。
- 将同一 ID 的远程元数据变化同步到已经加入播放列表的项目。
- 协议未保证的真正实时变更订阅。

## Key Risk Decision

方案 A 依赖 Navidrome 当前 `search3` 空查询的稳定自然顺序来实现通常只读取尾部。精确 ID 集合、尾部锚点、服务器/版本/音乐库指纹、扫描 token、分页重叠校验和完整核对回退负责检测可见异常。如果服务器在不改变这些校验信息的情况下改变旧位置歌曲顺序，或同一 music folder ID 内的可见范围在 API 没有暴露新指纹的情况下改变，OpenSubsonic 协议本身无法提供绝对的增量完整性保证；用户可用“完整核对”恢复。用户已接受该速度优先、异常回退的取舍。

播放列表与组件状态属于两个不同存储系统，无法形成真正的跨系统原子事务。实现通过主线程内同步追加、立即状态替换和失败补偿删除保证正常错误路径的一致性；进程在两步之间被强制终止仍是极小的残余窗口，列为已知限制。
